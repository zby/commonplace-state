I’d keep the build that omits frame pointers as the default and use the frame-pointer build in services where missing caller information has repeatedly hindered investigations.

The proposed build used 1% more CPU for the same requests in the usual-traffic replay. Changing the default would make that overhead routine for services that follow it. The diagnostic benefit is concrete, too. Of the ten investigations, four had a missing caller that mattered, and the proposed build revealed it in three of those four replays. That shows better visibility, but the team doesn’t know whether seeing the caller would have changed a diagnosis or saved substantial time. A third-party library can still interrupt the call chain.

The strongest reason to change the default is timing. Switching builds requires redeployment, so an investigator who discovers a gap during a transient incident may lose the chance to capture it. I’d therefore select the frame-pointer build *before* the next incident on affected services. On the evidence given, that risk justifies targeted use. I’d extend it to the default if experience showed that caller visibility regularly shortened important investigations enough to justify the recurring CPU cost.
