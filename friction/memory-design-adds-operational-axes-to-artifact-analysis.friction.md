# Friction check: Memory design adds operational axes to artifact analysis

**Note:** `kb/notes/memory-design-adds-operational-axes-to-artifact-analysis.md`
**Central claim (one sentence):** Memory-system design needs a second comparison layer of operational policy axes (capture, derivation, activation, authority policy, lifecycle, and evaluation) in addition to artifact-analysis fields, because the artifact fields identify what retained artifact exists but do not determine how retained material becomes usable memory over time.

## Filter
**Verdict:** SURVIVES

The note commits to one coherent claim: artifact fields and operational policies answer different questions, so memory comparison needs both. Its qualifications keep the claim narrow enough to remain consistent: the added axes are presented as a provisional checklist rather than a uniquely exhaustive basis, and the note says it is adding framing rather than replacing the underlying artifact taxonomy.

## Signal — thinnest joints
1. **"What is new here is the framing, not the underlying design pressures."** — UNSUPPORTED — The note names the proposed axes, but it does not show that prior memory discussions already contained the same pressures in another framing; the novelty boundary is asserted rather than demonstrated.
2. **"These fields are necessary because memory discussions often conflate them."** — THIN — The cited confusions support separating substrate, form, lineage, and authority, but they do not by themselves establish that those four fields are necessary for the later argument about adding six operational axes.
3. **"But artifact fields stop at the artifact boundary. They do not explain how retained material becomes future capacity."** — THIN — The examples show that artifact identity and authority-path distinctions matter, but the note does not fully rule out the possibility that some of the later operational questions could be represented as finer-grained lineage or authority analysis instead of a new axis family.
4. **"The same artifact fields can produce different memory behavior."** — THIN — The paired-system example makes the claim plausible, but it is hypothetical inside the note; it does not give an observed case where identical artifact-field descriptions still leave materially different memory behavior unresolved.
5. **"These policies cross component boundaries. Storage belongs to the execution substrate, activation belongs to the context engine, and learning and lifecycle decisions cut across both."** — THIN — The Rosebud reference supports the existence of multiple post-storage choices, but the component-boundary allocation is mostly asserted and would need a more explicit derivation or example to carry architectural weight.

## For the human
Look first at the boundary claim that artifact fields "stop at the artifact boundary": if that exclusion is not made sharper, the need for a separate operational-axis layer stays under-argued.
