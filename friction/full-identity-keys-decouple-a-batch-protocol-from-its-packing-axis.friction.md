# Friction check: Full-identity keys decouple a batch protocol from its packing axis

**Note:** kb/notes/full-identity-keys-decouple-a-batch-protocol-from-its-packing-axis.md
**Central claim (one sentence):** Keying each response block in a batched LLM-call protocol by the unit's full composite identity (e.g. `note_path :: gate_id`), rather than by position or a single-axis label, decouples the wire protocol from the grouping/packing strategy, so one grammar, renderer, and parser handle any grouping axis or mix of axes without a format change.

## Filter
**Verdict:** SURVIVES

The claim wants two things that can look like they trade off: (1) a single, fixed, simple wire format ("one grammar, one renderer, one parser") and (2) permanent openness to grouping strategy, including axes not yet in play ("a new axis... needs no format change to add"). A fixed concrete key shape (a two-part tuple, per the worked example) and unlimited future extensibility look like the "as fast as C and as dynamic as Lisp" pairing: pick a closed shape and you get simplicity now, pick genuine open-endedness and you need a more general (variable-arity or opaque) key structure than the one-tuple example shows.

It survives rather than dissolves because the note's actual mechanism doesn't require unlimited future openness to hold — it requires only that the identity space used for grouping is already fully spanned by the key at the time the grammar is fixed. Read that way, "full composite identity" is doing real, load-bearing work: as long as every dimension a caller might batch along is already a component of the key, any subset or recombination of those dimensions groups for free, with no format change. That is one consistent thing the note commits to. The overreach is narrower than a full dissolution: the note's phrasing ("a new axis... needs no format change to add") states a stronger, unrestricted version of this than the mechanism actually delivers — genuinely novel dimensions of identity, not yet present in the key, would still require extending the tuple. That gap is real but is a single overstated corollary, not a split into two incompatible central claims, so it is recorded as a Signal joint below rather than a Filter-level dissolve.

## Signal — thinnest joints

1. **"so a new axis, or a mix of axes, needs no format change to add"** — UNSUPPORTED — This is the note's most concrete, testable claim, and it overreaches past what the argument establishes. The supporting sentence just before it only shows that coverage checking, ordering, and failure attribution don't depend on *which existing* identity dimension a call groups by — that licenses "any recombination of already-keyed dimensions is free," not "any new axis is free." The worked example (`note_path :: gate_id`) is a fixed two-part tuple; a genuinely new, independent dimension of identity (e.g. a third axis like reviewer or workshop) is not latent in that tuple and would require extending the key shape — a format change the sentence explicitly denies is needed. Nothing in the note distinguishes "new axis drawn from the existing full-identity space" from "new axis not yet part of that space," and the claim needs that distinction to be true as written.

2. **"Supporting a second axis then means a second renderer, a second parser, and a second failure policy, because the grammar has no way to say which axis produced a given block."** — THIN — The "because" clause establishes that a purely positional grammar is ambiguous about which axis produced a block. It does not establish that the fix requires three whole separate systems (renderer, parser, *and* failure policy). A lighter patch — e.g. adding an explicit axis-discriminant field to the existing positional grammar — could resolve the ambiguity without tripling the implementation. The leap from "the grammar is ambiguous" to "you need a full duplicate stack" is stronger than the stated reason supports; it also has the effect of making the note's own solution look more necessary by inflating the cost of the alternative.

3. **"A parser that must infer identity from position or from surrounding call context cannot recover cleanly from a single dropped or reordered block"** — THIN — "Cannot recover cleanly" is stated categorically. A positional parser that also knows the expected count of blocks can often detect *that* something is missing or reordered (a count mismatch, an out-of-range position) even without full identity — it just can't always attribute *which* unit failed. The note's claim is directionally right (full-identity keys give strictly more recoverable information) but overstates the positional baseline as recovering nothing, when the real gap is between "detects a problem" and "attributes the problem to a specific unit."

4. **"It matters more for a batched LLM-call protocol, because parsing there is probabilistic reconstruction of a keyed structure from free text rather than a deterministic decode"** — HOLDS — The comparative argument is tight: exact, cheap decoding (JSON-RPC, GraphQL) genuinely differs in kind from reconstructing structure from a model's free-text output, which can reorder, omit, or duplicate blocks in ways a deterministic decoder cannot. The "matters more, not less" framing is earned by a real mechanism, not just asserted.

5. **"One grammar, one renderer, one parser work regardless of which axis groups units into a call, because coverage checking, ordering, and failure attribution never depend on position or on which axis produced the group."** — HOLDS — Given a key that already spans the relevant identity dimensions, this is close to definitional: if none of coverage, ordering, or failure attribution reads position or axis, then the same code path is axis-agnostic by construction. This is the strongest joint in the note; its only weakness is the one flagged in joint 1 (it doesn't cover identity dimensions the key doesn't yet include), which the note conflates with it in the next sentence.

## For the human
Start with joint 1 — "a new axis... needs no format change to add" is the note's sharpest, most citable claim, and it silently assumes the new axis was already latent in the "full" identity key rather than genuinely new; that's the missing concretization worth asking the author about.
