# Friction check: Runtime structure determines the control surfaces available to governance

**Note:** kb/notes/runtime-structure-determines-governance-control-surfaces.md
**Central claim (one sentence):** Runtime structure and runtime governance are distinguishable questions, but they are not independent — the runtime's structural decomposition (scheduler, context engine, substrate) determines which inspection, validation, correction, and drift-detection operations governance can perform, and governance in turn slowly hardens structure over time.

## Filter
**Verdict:** SURVIVES

The note wants "distinguishable axes" and "asymmetric dependence" at once, which looks like the classic have-it-both-ways move, but it heads this off explicitly in its own opening line ("'separate axes' can be misleading if it implies independence") — it never actually claims independence, only that the two are different *questions* asked of the same system. A determination relation running one direction (structure bounds governance now) coexisting with a slower feedback loop running the other direction (governance reshapes structure over cycles, via "hardening") is not a logical contradiction — it's an ordinary two-timescale causal loop, not a "fast as C and dynamic as Lisp" simultaneous-incompatible-properties claim. There is no pair of properties here that cannot coexist; the note's own "layered relationship" framing is the correct resolution, not a fudge covering an unresolved tension. The claim survives concretization as a determination-plus-feedback relation.

## Signal — thinnest joints

1. **"That is a design boundary, not a gap: governance can only act on what commonplace actually owns, so the empty row is itself evidence for this note's claim rather than an exception to it."** — UNSUPPORTED — This converts the one concrete counterexample in the note (an entire matrix row with no governance operations at all) into confirming evidence, with no independent test that could have gone the other way. If a control-surface deficit is simultaneously the strongest available demonstration of "structure determines governance surfaces," nothing the note could observe would count against the claim — an empty row reads exactly the same whether the theory is true or false. This is the single weakest joint in the note: it does the work of a load-bearing example while functioning as an unfalsifiable rescue.

2. **"Governance is not free-floating. It can only operate through the control surfaces the runtime's structure exposes."** — THIN — This is the note's central thesis stated as a premise rather than derived. The "only" is a strong universal claim: it rules out, without argument, any governance channel that isn't a structural control surface exposed by scheduler/context-engine/substrate — e.g., a human operator reading logs out-of-band, a norm enforced socially among agent maintainers, or an external monitoring system bolted on without being part of the runtime's own decomposition. The note needs "only" to make the rest of the argument (matrix, comparison claim) go through, but never argues why no non-structural governance channel could exist; it is asserted at the point where the whole note's leverage comes from it.

3. **"This is the strongest governance surface because exact external state is easier to validate than hidden internal state."** — THIN — The comparative superlative ("strongest") among the three structural components' governance surfaces is not actually argued against the other two. The scheduler paragraph shows explicit scheduling affords governance (retry limits, delegation boundaries, escalation paths) and the context-engine paragraph shows explicit context selection affords governance (routing audits, compaction review) — both described in comparably strong terms. Nothing in the text establishes that "easier to validate than hidden internal state" makes the substrate's surface *stronger* than an equally explicit scheduler's or context engine's surface, only that it is strong in an absolute sense. The ranking move is asserted, not derived from a comparison of the three.

4. **"Two runtimes can have similar structure but very different governance capacity because one externalizes its state and decisions while the other leaves them implicit."** — THIN — This generalizes from the single-runtime, single-axis observations above (substrate, scheduler, context engine considered separately within one system) to a comparative claim across *two different runtimes* with "similar structure." No second runtime is named or contrasted; the only worked example offered anywhere in the note is commonplace itself, examined alone, not against a structurally-similar counterpart with different externalization choices. The inference is plausible but the note supplies no comparative case to ground it.

5. **"That is why governance should not be modeled as a fourth peer component beside scheduler, context engine, and substrate... The role is supervisory, not a separate execution slot in the runtime anatomy."** — THIN — The support offered is that governance functions "cut across components" (review inspects the context engine's output, compares substrate artifacts, alters scheduling). Cross-cutting-therefore-not-a-peer-component is a standard architectural intuition (aspect vs. layer), but it is an analogy, not a demonstration — a cross-cutting concern can still be modeled as its own component with cross-cutting *interfaces* (e.g., a "governance" service that owns state, budgets, and policy even while touching every other component). The note doesn't rule this modeling choice out; it asserts the conclusion follows from cross-cutting-ness alone.

## For the human
Start with joint 1 — the empty scheduler row is doing double duty as the note's one concrete test case and as an unfalsifiable confirmation of the thesis; decide whether the note needs an actual disconfirming case (a structure with a genuine ungoverned surface) before the "structure determines governance surfaces" claim can be trusted beyond restating itself.
