# Critique: Full-identity keys decouple a batch protocol from its packing axis

**Note:** kb/notes/full-identity-keys-decouple-a-batch-protocol-from-its-packing-axis.md
**Central commitment:** Keying every batch response block by a unit's full composite identity (e.g. `note_path :: gate_id`), rather than by position or a single axis, fully decouples the wire protocol from the packing axis — so a new axis, or a mix of axes, needs no format change to add.
**Critique mode:** claim

## Strongest case against it

An informed protocol designer in the "self-describing envelope" tradition — someone who has built generalized multi-key batch/RPC formats (variable-arity `$batch` requests, keyed union types, tagged JSON envelopes) — would argue the note has swapped one coupling for a subtler one and called it decoupling.

The concrete instance the note generalizes from, ADR 029, keys every block with a **fixed two-field string concatenation**: `{note_path} :: {gate_id}`, joined by a hardcoded ` :: ` separator, parsed by splitting on that separator. That is not an axis-agnostic key scheme; it is a *hardcoded 2-tuple* scheme. Two costs the ADR itself pays make this concrete:

1. **Arity is baked into the parser.** `parse_pair_bundle` knows to split each sentinel into exactly two components. If a third axis genuinely needs to vary independently within the same job — say, batching (note, gate, reviewer) triples instead of pairs — the parser's split logic, the sentinel grammar, and the coverage-check logic (which now must track 3-tuples, not 2-tuples) all have to change. That is a format change triggered by adding an axis, which is precisely what the note claims a full-identity key protocol avoids ("a new axis... needs no format change to add"). The note's own worked example never actually exercises a third axis; it generalizes "no format change" from a system that has only ever had two.
2. **The key's value space is now constrained by the protocol.** ADR 029 states plainly: "The ` :: ` separator is rejected in note paths and gate ids at render time, as are reserved `=== … ===` sentinel lines inside embedded note or gate text." This is a coupling running the *other direction* — the wire grammar now restricts what characters a domain identity (a note path, a gate id) is allowed to contain. A protocol that must reserve characters out of the domain's value space to remain parseable is not "one grammar... regardless of which axis groups units" — it is one grammar for axes whose values happen to avoid the delimiter. The note presents the decoupling as clean; the source it draws from shows the coupling didn't vanish, it moved from "position in the block" to "characters the identity fields may not contain."

The stronger opponent's summary claim: string-concatenated composite keys buy independence from *position* and from being locked to a *single named axis*, but they do not buy independence from the *number* of axes or from the *value space* of each axis component — both of which a truly axis-agnostic protocol (e.g., a self-describing key such as a small tagged map `{note_path: ..., gate_id: ...}` with named, escaped fields) would need to handle without a parser/grammar change. The note's title claims the general case; its only grounding is a fixed-arity, character-restricted special case, and the two costs above are exactly where a third axis or a delimiter-containing identity would break the "no format change" promise.

## How the note engages it

Unengaged. The note's "Open Questions" section raises a different, narrower concern — whether the *payload requested per block* stays axis-invariant when content legitimately differs by axis (e.g., a cross-item comparison field). It never addresses whether the *key grammar itself* stays axis-count-invariant, nor whether the identity components are free of value-space restrictions. The "Scope" section disclaims only prompt-quality and efficiency tradeoffs ("which axis... produces the best prompt quality"), not protocol-level costs like delimiter reservation or parser re-arity. ADR 029's own "Consequences" section names both costs this critique relies on (the reserved-character render failure, and "the pair key repeats the shared axis in every sentinel — a small token cost") but the note synthesizes only the positive half of that ADR (§5, "batching is a packing choice, not a protocol") and drops the accompanying costs.

## Constructive findings

- Distinguish, in the body or a new subsection, between what full-identity keying actually buys (position-independence, single-axis-independence) and what it does not (arity-independence, delimiter/value-space-independence). The current wording ("needs no format change to add") oversells past what the ADR 029 grounding demonstrates.
- Name the value-space cost explicitly: a string-concatenated composite key requires reserving the delimiter (and any structural sentinels) out of every component's domain, which is itself a coupling between protocol and content — the mirror image of the coupling the note claims to remove. A reader evaluating whether to adopt this pattern needs that cost in view, not just in the linked ADR's consequences section.
- Either restrict the claim to "axis choice and axis count fixed at design time" (matching what ADR 029 actually shows), or strengthen it by pointing to — or specifying — a key encoding that is genuinely arity-agnostic (e.g., a tagged/self-describing key rather than a fixed-delimiter concatenation), and note that the concatenated-string version is one implementation choice among several, with the arity limitation being specific to it.

## Secondary objections (optional)

- Coverage-checking ("detect exactly which units are missing or duplicated") requires the caller to already enumerate the full set of expected identities before the call returns. That's a real requirement the note doesn't foreground: the flexibility is in *how* axes are chosen when *constructing* the call, not in the parser discovering axes it wasn't told to expect. This is a lesser point since it's arguably implicit in "policy chosen by the caller," but the note's framing ("removes that coupling" without qualification) invites the stronger reading this critique attacks.
- The note's "old wisdom" framing (JSON-RPC request ids, GraphQL aliases) undercuts its own novelty claim somewhat — those systems also use string or numeric keys with reserved-character/escaping rules (e.g., GraphQL alias syntax restrictions), so the value-space coupling identified above is not unique to the LLM case either; it's a general property of delimiter-based composite keys that the note doesn't credit to the prior art it cites.
