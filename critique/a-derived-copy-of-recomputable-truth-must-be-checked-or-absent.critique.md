# Critique: A derived copy of recomputable truth must be checked or absent

**Note:** kb/notes/a-derived-copy-of-recomputable-truth-must-be-checked-or-absent.md
**Central commitment:** Any artifact carrying a mechanically-recomputable copy of ground-truth information must be either machine-checked (a validator re-derives it and fails on mismatch) or absent (deleted, or replaced by a live read) — hand-maintained-and-trusted is a forbidden third state.
**Critique mode:** claim

## Strongest case against it

This is the regress objection that experienced verification engineers raise against every "the check makes it safe" rule — the same objection formal-methods skeptics raise against "the tests pass so it's correct," and SREs raise against "the linter is green so the config is valid." A validator is code. Code is itself an artifact that carries a claim — "this derivation rule correctly re-derives the copy from the source" — and that claim is exactly as recomputable-from-ground-truth as the copy it replaces (the "ground truth" here being the intended semantics of the source, e.g., what "tagged with X" *should* mean). Nothing in the note's own dichotomy applies recursively to the validator itself: the validator is not machine-checked against a meta-validator, and it is not absent. It is a hand-maintained, human-authored, trusted artifact — precisely the third state the note forbids, just relocated one layer down.

This is not a merely notional regress; it bites on the note's own flagship "already enforced" instance. The `complete`/`covered_by` marks on tag-READMEs are checked by re-deriving membership from "the scoped `rg` sweep" (§ Instances). But an `rg` pattern encoding "what counts as this note carrying this tag" is itself a judgment call, hand-written once and then trusted forever: false negatives (a note using the concept without the exact tag string, or the tag inside a code fence, or a synonym) and false positives (a tag string appearing in prose quotation rather than frontmatter) are exactly the silent-wrongness failure mode the note's asymmetry argument condemns — except now it's worse, because "checked" carries a *stronger* trust signal than "hand-maintained." By the note's own asymmetry logic (§ "The asymmetry that forces the rule": a trusted-but-stale claim "tells consumers to stop looking"), a buggy validator is more dangerous than an openly-unenforced hand-maintained copy, because readers who know a copy is unenforced retain some default skepticism, while readers told "a validator checks this" stop looking entirely. The rule's cure inherits the exact disease it was built to eliminate, and inherits it with a stronger trust halo attached.

A second, related prong: the note claims "the economics that excused the unchecked copy disappear — trusting it saves nothing" once the check is mechanically cheap (§ "Where the rule applies"), treating validator cost as effectively zero. But authoring, testing, and maintaining the validator itself (and keeping its derivation rule in sync with the source's evolving shape — the `rg` pattern must be updated if tagging conventions change) is non-zero engineering cost that the note never enters into its ledger. For a low-traffic copy, that authoring/maintenance cost can exceed the expected loss from occasional staleness over the artifact's lifetime — an expected-value argument the note's worst-case framing ("forbidden," "no safe middle") doesn't engage at all.

## How the note engages it

Unengaged. The three preconditions in "What 'checked' requires — and its limits" (derivation rule, machine-locatability, ground truth existing at validation time) govern whether the *copy* qualifies for enforcement, but none of them asks whether the *validator* itself is correct, tested, or subject to its own drift — the regress simply isn't in scope. The "Instances" section presents the tag-README marks as unambiguously "enforced and shipped" without acknowledging that the `rg`-sweep derivation rule is a hand-authored heuristic standing in for the real ground truth ("does this note carry this concept"), which is the same gap the note attacks everywhere else. The "Consequences" section ("Checked copies degrade gracefully") only discusses the cost of *dropping* a checked copy, not the cost of a *wrong* validator. Nothing in the Open Questions section names this either — the two open questions (unenforced natural-language claims elsewhere; cheapest mechanism for frontloaded regions) are adjacent but don't ask "what checks the checker."

## Constructive findings

- Add a fourth precondition (or a caveat under "What 'checked' requires") addressing validator-correctness regress directly: state why it's expected to bottom out rather than recurse — e.g., a validator is centralized, versioned, code-reviewed on every change, and amortized across many copies, so its unit cost of correctness-assurance is far lower per-copy than N hand-maintained instances would be. That's a real argument but it needs to be made, not assumed.
- Acknowledge that "checked" is not risk-free — it converts a visible, appropriately-distrusted risk (an admittedly hand-maintained copy) into an invisible, over-trusted one (a validator bug) — and say what bounds that risk (validator tests, narrow/literal derivation rules preferred over heuristic ones like `rg` sweeps, or a periodic manual audit of the validator's own hit/miss rate).
- Revisit the tag-README instance with this lens: is the `rg` sweep a "derivation rule" in the strict sense precondition 1 requires ("Extractable lists, set memberships... qualify; natural-language summaries and judgments do not"), or is it itself a judgment-laden heuristic wearing mechanical clothing? If the latter, the note's one fully "enforced" instance is weaker evidence than presented.
- Count validator-authoring/maintenance cost explicitly against the "trusting it saves nothing" claim in "Where the rule applies," at least as a bounded caveat for low-traffic or rarely-changing copies, rather than treating Level A check cost as uniformly free.

## Secondary objections (optional)

- Practice-contradicts-rule: of the note's own four instances, only one is actually in the "checked" state; the other three are "stated but unenforced," "resolved by omission," and "not yet applied" — i.e., hand-maintained-and-trusted (or its cousin, unenforced-and-hoped) is the de facto majority state even inside the system that proposes forbidding it. That's suggestive evidence the rule is harder to fully realize in practice than the "forbidden" framing implies.
- The note treats "checked or absent" as an exhaustive binary, but doesn't consider partial/graduated enforcement (e.g., a validator that runs only in CI, not on every edit; or one with known blind spots that are tracked as debt) — a real middle ground between fully checked and fully absent that many systems actually run on.
