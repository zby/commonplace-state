# Critique: Agent orchestration needs a privilege quarantine, not just a permission scope

**Note:** /home/zby/llm/commonplace/kb/notes/orchestration-needs-privilege-quarantine-not-permission-scope.md
**Central commitment:** When an orchestrated agent's context includes untrusted, attacker-reachable content, the correct defense is a *role-level* privilege quarantine (a permanently unprivileged reader role separated from a privileged actor role) — because per-call permission scoping is structurally incapable of reaching "which content is allowed to steer a call," not merely poorly tuned to do so.
**Critique mode:** claim

## Strongest case against it

The strongest opponent is a security engineer working in the taint-tracking / information-flow-control (IFC) tradition of prompt-injection defense — the line of work exemplified by capability-and-provenance systems for agent tool calls (e.g. the "dual LLM" pattern and its formalizations, where a runtime attaches provenance/capability metadata to every value and a policy engine decides, per call and per argument, whether that specific call is permitted given where its inputs trace back to). This opponent's stance: **the note's central dichotomy is false**. "Permission scope" as the note defines it (tool-identity scoping: which tools may this call use) is a strawman version of per-call scoping. The real state of the art scopes calls on data *provenance*, not tool identity — a call to a privileged tool is blocked not because the tool is off-limits to the caller's role, but because this particular invocation's arguments are tainted by untrusted content. That is still a per-call check. It just checks something richer than the note assumes per-call checks can check.

Under this view, privilege quarantine is not a different *kind* of defense from permission scoping — it is the degenerate, coarsest-grained special case of provenance-aware scoping, where the scope function collapses to two buckets ("reader role → deny all privileged tools," "actor role → allow, but only on reader-vetted input") instead of a continuous function of actual data lineage. If you can build the finer-grained version — and taint-tracking capability systems claim to — then the note's strong claim that the problem is "architectural, not a matter of tuning the permission list" is simply overstated. It is a matter of what the permission list is allowed to condition on. A role split becomes an engineering convenience for approximating provenance tracking cheaply, not the only architecture that reaches the threat.

This is not a hedge — it names a concrete, existing category of defense (provenance/taint-based capability enforcement) and a concrete claim (the note's "cannot" is actually "does not, under the narrow definition of scoping assumed here").

## How the note engages it

Partially engaged, and the partial engagement is telling.

The note's own argument in "Why per-call scoping doesn't reach this" (para starting "Quarantine is the same gap read one level down...") explicitly uses the word *provenance*: "a per-call permission check authorizes an *action*, not the *provenance of the content that chose it*." So the note has the concept in view. But it does not argue why a per-call check is structurally barred from being made a function of provenance — it asserts it: "nothing in the per-call check asks where the instruction that shaped this call came from." That's a description of *today's typical* per-call checks (tool-identity ACLs), not a proof that per-call checks in general cannot incorporate provenance. The taint-tracking counter-architecture is exactly a per-call check that does ask that question. The note never names or rules out this category — it moves straight from "typical scoping doesn't ask about provenance" to "the boundary must move to the role level," without addressing the middle path of making scoping provenance-aware instead of moving the boundary.

The "Scope limit" section comes closest to adjacent territory — it concedes the actor "trusts the reader's structured output completely" and gestures at needing "its own oracle" to check the reader's extraction against the source. But this is about quarantine's *own* residual risk (a compromised reader deceiving a trusting actor), not about whether a provenance-scoped single-role architecture could have addressed the original threat without a role split at all. It's a different question, addressed in the note, that only superficially resembles this critique's question.

The Open Questions section flags "no adversarial red-team measurement" of quarantine's effectiveness — an honest limitation, but again not a response to the specific claim that a competing, already-fielded class of architecture (provenance/taint-based per-call enforcement) might reach the same goal without the role split.

**Verdict: partially engaged.** The note has the vocabulary (provenance) in hand but treats "per-call scoping" as definitionally tool-identity-only, never considering or ruling out provenance-conditioned per-call scoping as a distinct third option between naive tool ACLs and full role quarantine.

## Constructive findings

- Name the competing architecture explicitly (provenance/taint-tracking capability enforcement, e.g. dual-LLM-style systems where a policy engine gates calls on argument lineage) and explain why it collapses back into quarantine rather than refuting it — likely candidate answer: LLM "steering" via diffuse in-context influence (an instruction that changes the agent's *judgment* without any tainted value being literally passed as a call argument) is not mechanically traceable the way variable-level taint tracking works in a programming-language interpreter, so a single agent that both reads untrusted content and acts cannot be safely gated by argument-provenance checks alone — you still need a role that never lets the untrusted content reach the reasoning that decides the call at all. If that's the real defense, the note should make it, because right now the "cannot" is asserted rather than derived.
- Distinguish "per-call scoping keyed to tool identity" from "per-call scoping keyed to data provenance" as two different things before dismissing "per-call scoping" wholesale — otherwise the note's dichotomy reads as attacking the weaker of the two.
- If the author's position is that quarantine is the *practical* answer (cheap, robust, doesn't depend on solving the hard problem of tracking taint through an LLM's reasoning) rather than the *only conceivable* answer, say so — that's a defensible, narrower claim than "architectural, not a matter of tuning," and it would preempt this attack directly instead of needing this report to surface it.

## Secondary objections (optional)

- The note weighs quarantine's benefit but not its cost: a mandatory role split adds latency, duplicated inference calls, and — more substantively — a lossy compression step (the reader must reduce untrusted content to "structured, already-vetted output" before the actor ever sees it). Content nuance dropped at that boundary is unrecoverable by the actor, which is a cost the note doesn't set against the alternatives it dismisses.
- The evidentiary base is two first-party accounts (the dynamic-workflows triage pattern and GBrain), both cited as independent convergence — the note is already explicit about this being "established by convergent design, its effectiveness as untested" (Open Questions), so this is a known and disclosed limitation rather than a hidden one, but it's worth flagging that "convergence" here is convergence of *design intuition*, not of measured outcomes, which is weaker support for a strong architectural "the reason is X, not Y" claim than the note's confident tone implies.
