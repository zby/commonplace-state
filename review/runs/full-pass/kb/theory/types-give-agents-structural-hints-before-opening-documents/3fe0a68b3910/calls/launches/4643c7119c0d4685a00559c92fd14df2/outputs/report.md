# Premise decomposition: Types give agents structural hints before opening documents

**Note:** kb/theory/types-give-agents-structural-hints-before-opening-documents.md
**Register:** claim
**Central commitment (one sentence):** Document types, together with descriptions, give a stateless agent structural hints it can read before opening a document, so it can make an informed load/skip routing decision and narrow hundreds of files to the few it needs without opening them.

## Premises and counterexamples

1. **An agent can read a document's type without opening the document (universal, unstated).** — DOUBTFUL — In this KB, `type:` is a frontmatter field inside the file. The navigation surfaces the repository actually uses (`rg` over titles and descriptions, generated indexes, tag READMEs, link text) usually show title and description but not type. Reading `type:` takes either a frontmatter read, which partly opens the file, or a grep/index step that someone must build to expose it. The note never says which surface delivers the type before opening. As written, "before opening" holds for descriptions shown in indexes, and less clearly for types. — LOCAL (name the surface, such as frontmatter-only reads or an index that renders type; the commitment survives if such a surface exists) — instance

2. **Types discriminate among the documents an agent is choosing between, so knowing the type changes the routing decision (universal, unstated; the commitment rests on it).** — DOUBTFUL, close to DEFEATED for this KB's own theory collection — In `kb/theory/`, about 395 of about 440 files declare `type: types/note.md`. Only a handful use `structured-claim`, and the rest are definitions or proposals. Inside a collection, which is where most routing decisions happen, type is nearly constant and carries almost no bits. Title, description, directory placement and traits do the narrowing. The examples the note gives (`spec`, `structured-claim`, `index`) mostly describe a richer type set than the one this KB actually populates. `spec` and `index` are not current shared types in `kb/types/`. The type adds information mainly *across* collections, and there directory placement already conveys most of the same signal. — GLOBAL (type's share of the "narrow from hundreds to few" result is the note's thesis. If routing is carried by description, title and directory, the commitment must be reframed: types contribute a coarse affordance prior, and descriptions do the filtering) — prevalence

3. **The type's structural promise maps onto an operation the agent wants to perform (e.g. "has Evidence/Reasoning sections" means "I can extract a citable argument") (universal).** — DOUBTFUL — The mapping holds for strongly structured types such as `structured-claim`, `instruction` and `ingest-report`. The base `note` type promises little structure beyond frontmatter and a body, so knowing a document is a `note` affords no specific operation. The affordance premise holds in proportion to how much structure each type commits to, and the most common type commits to the least. — LOCAL (scope the claim to types with section-level contracts) — prevalence

4. **Without types, an agent must either load everything or guess (universal, stated as a dichotomy).** — DEFEATED — A concrete third route is routing on titles and descriptions alone, plus directory placement, search hits and link context. That route uses no type. The note itself makes descriptions the instance filter, and descriptions do not require types: a KB could require a description field with no type system at all, as many front-matter-only wikis do. "Without types" therefore does not force the dichotomy. Only "without any pre-open metadata" does. — LOCAL (restate the contrast as "without pre-open metadata"; this weakens the motivation for types specifically but leaves the routing mechanism intact) — instance

5. **Agents are stateless across sessions, so they cannot route from memory of prior reads (universal).** — HOLDS for current harnesses at the level the note needs. Persistent memory files and always-loaded context can carry some routing knowledge. That knowledge is itself pre-open metadata, so it does not undercut the need for cheap hints. The hunt found no case where cross-session memory removes the need to decide what to open.

6. **Descriptions function as instance-level retrieval filters, distinguishing the relevant document among those of the same type (universal).** — HOLDS with a caveat — Well-written descriptions do this. A description that summarizes instead of discriminating fails it, but the note cites the base-type rule that requires the filter form, so the premise is conditioned on that rule being followed. The quality of the filter depends on writing discipline, not on the type.

7. **Verifiable (structural) types are what make type-based routing informed rather than blind (universal).** — HOLDS — A subject-matter label cannot be checked and carries no operation, so the contrast with "this is a design note" stands. This premise strengthens premise 3 but does not rescue premise 2: a verifiable type that nearly every document shares is still uninformative for choosing among those documents.

8. **The type system is what makes descriptions exist reliably (universal, stated in the last paragraph).** — DOUBTFUL — Validation of the required frontmatter makes descriptions exist. That check can be a schema or linter independent of a type taxonomy, for example a single universal "every file has a description" rule. Enforcement is one function a type system can host, but it is not the only host. The causal attribution to "the type system" is stronger than needed. — LOCAL (say "metadata enforcement, here hosted by the type system") — instance

## For the human

Look first at premise 2. In this KB's own theory collection almost every document is `types/note.md`, so type barely discriminates during routing, and descriptions, titles and directories do the narrowing. Decide whether the note should claim that types give a coarse affordance prior across collections, or argue for a richer populated type set.
