# Connection Report: The code IS the graph (Samuel Colvin, X thread)

**Source:** [The code IS the graph](../../../../sources/.snapshots/the-code-is-the-graph-2110055467007303729.md)

The source is an immutable snapshot. Every outbound candidate below is a recommendation for its authored surface, the future `kb/sources/the-code-is-the-graph-2110055467007303729.ingest.md`. That ingest did not exist when this run started. Labels come from the `kb/sources/COLLECTION.md` Outbound links table.

**Source claim, as read for discovery:** Executable graph libraries are a mistake for agent orchestration, because host-language structured control flow already serves as the graph and the call stack already holds the run state. The thread offers a "typed / parallel / snapshotted: pick two" trilemma. Parallel nodes that mutate shared state leave no coherent snapshot point except at a barrier. Making the state snapshot-safe forces per-field merge rules (reducers), and no type checker can verify those. The thread names three escapes:

- Temporal replays the code against recorded activity results.
- Monty, a sandboxed interpreter that holds no OS resources, serializes its whole heap and call stack at each pending host-function call.
- Writing the join as typed code: `a, b = await gather(...)`, followed by an explicit merge line.

In Pydantic AI Harness, an orchestrator model writes the choreography through one `run_workflow` tool. The script is type-checked against sub-agent signatures before it runs and can be rewritten on every turn.

## Connections Found

### Notes

- [The practical scheduler is the host language, not a reified select](../../../../notes/the-practical-scheduler-is-the-host-language.md) -- **is-evidence-for**: This is the closest claim-match in the KB.
  - **Same core claim:** The author of pydantic-graph argues independently that host-language control flow already serves as the scheduler, and that a graph library reifies the run state worse than the call stack does.
  - **Evidence for the Scope section:** The source bears on the note's Scope section, which says K must be reified when the run outlives its process. It shows two routes that make K durable without application-level reification. Temporal re-derives K by replaying code against recorded activity results. Monty serializes the interpreter heap and call stack at host-call barriers.
- [Any barrier-delimited symbolic program with LLM calls is a batched select/call program](../../../../notes/any-symbolic-program-with-llm-calls-is-a-select-call-program.md) -- **is-evidence-for**: This is a practitioner account of the lemma's preconditions and of its "Non-LLM effects need separate semantics" section.
  - The source argues that parallel in-place state mutation leaves no coherent snapshot point "except a barrier where nothing is in flight".
  - It says the runner cannot tell whether a node "sent the email". Both Temporal activities and Monty host functions are the boundary where an author declares whether retry is safe.
  - It separates typed output joins (`gather`) from untyped state joins (reducers). This matches the lemma's "explicit merges fit" scope.
- [LLM↔code boundaries are natural checkpoints](../../../../notes/llm-code-boundaries-are-natural-checkpoints.md) -- **is-evidence-for**: Monty makes every external function call a snapshot point and a resume point. A paused `gather` is one snapshot with three pending calls, which can be resumed in another process by handing back their results. This is a shipped-runtime instance of the boundary as a replay point. The source's caveat that the host function decides retry safety matches the note's Scope warning that replay needs external dependencies.
- [RLM has the model write ephemeral orchestrators over sub-agents](../../../../notes/rlm-has-the-model-write-ephemeral-orchestrators-over-sub-agents.md) -- **compares-with** (axis: the substrate for model-authored orchestrators): Pydantic AI Harness `run_workflow` is RLM's pattern, in which the model writes the orchestrator rather than acting as it, with two additions:

  - It runs on a snapshot-resumable sandbox.

  The source also endorses the ephemerality RLM is criticised for: "the graph can be rewritten on every turn".
- [RLM, λ-RLM, Tendril, and llm-do separate restriction from persistence](../../../../notes/rlm-tendril-and-llm-do-place-symbolic-work-at-different-persistence.md) -- **compares-with** (axis: control-language restriction): Monty is a new point between RLM's arbitrary REPL and λ-RLM's typed combinator menu. It accepts general Python, exits only through host-registered functions, and is checked against typed sub-agent signatures. Its persistence is within-run (a snapshot or Temporal replay), not cross-run promotion.
- [Orchestration strategies and run-state have opposite persistence economics](../../../../notes/orchestration-strategies-and-run-state-have-opposite-persistence.md) -- **compares-with** (axis: which half of the scheduler is made durable): The source invests only in within-run durability of K (Temporal and Monty) and treats the model-written `select` script as disposable. ## Synthesis Opportunities

Several existing notes and sources together point toward a claim the KB does not yet hold: a durable-execution design chooses which state it makes coherent, and each choice limits what a type checker can verify. The inputs are:

- the-practical-scheduler's Scope section, which says K is reified when lifetime or capacity breaks
- the select/call lemma's effects section
- the Claude Code dynamic-workflows journal
- ADR 113's declared plans with one owner per path
- this source's trilemma

Three strategies appear in that material:

| Strategy | What it makes durable | Instances |
|---|---|---|
| Re-derivation by replay | Effect results only | Temporal, the CC workflow journal |
| Whole-interpreter snapshot at host-call barriers | The entire interpreter state | Monty, the Prime Agent kernel snapshot |
| Reified state with merge rules or disjoint ownership | Application state | LangGraph reducers, ADR 113 path ownership |

A future writer could test whether this belongs as an extension of the practical-scheduler Scope section; fold it there rather than spawning a satellite note. Connect does not create it.

## Maintenance Observations

- The practical-scheduler note's Scope paragraph claims that a lifetime mismatch makes reifying K "no longer optional". The source shows two mechanisms that keep K implicit in code while still surviving process death:
  - Replay re-derives K from recorded effect results.
  - A resource-free interpreter serializes the live call stack.

  The note may overstate this boundary. Reification of the *operative* K is avoided in both cases, although a journal or snapshot is persisted. This is a candidate for a revise pass on that note.
- The tags collection has no concept for executed graphs versus code as the graph, or for durable execution. Several KB artifacts treat replay (ADR 113, the archived code-scheduled-workflows proposal, the CC workflows review, Eigenius), but no note names replay-based durability as a mechanism. This is a repeated unnamed mechanism.
