# Premise decomposition: Reading HCL as deployment-time learning

**Note:** kb/work/causal-impact-selective-evaluation/hcl-reading.md
**Register:** claim
**Central commitment (one sentence):** HCL is aptly classified as deployment-time learning because post-execution evidence selects and retains operative harness changes without updating model weights, but HCL's four-part partition still does not justify selective evaluation by local causal impact.

## Premises and counterexamples
1. **Architecture alone is enough to classify HCL as deployment-time learning even though the evidence comes from a controlled sequential benchmark stream rather than live deployment.** — DEFEATED — An offline replay harness that proposes prompt and routing edits from prior benchmark failures, rejects candidates that violate an anchor budget, and commits accepted edits for the next replay batch has the same search-evaluation-retention structure, but it is still an offline benchmark optimizer rather than deployment-time learning. Architecture alone therefore does not force the deployment-time label. — GLOBAL — instance
2. **Commonplace's stated boundary for deployment-time learning is strong enough to separate learning from merely durable maintenance: evidence must bear on selection, and accepted retained state must later shape behavior.** — DOUBTFUL — A governed service that proposes prompt patches from yesterday's failures, reruns only a narrow replay set, and deploys whichever patch passes would satisfy that boundary while still plausibly reading as tightly managed maintenance rather than learning; the note does not add a stronger criterion that rules that case out. — LOCAL — instance
3. **In HCL, post-execution evidence from prior task executions actually drives candidate harness revision rather than merely documenting edits chosen on other grounds.** — HOLDS — The strongest counterexample would be manual or random edits independent of prior executions, but the note describes optimizer-driven candidate construction from post-execution evidence.
4. **HCL's evaluator is genuinely reject-capable: it can refuse adoption unless current-task improvement, sampled historical retention, and validity all hold together.** — HOLDS — Unsampled regressions do not defeat this premise because they limit the gate's warrant domain, not its ability to block a candidate on the checks it does run.
5. **Accepted HCL revisions become operative retained state in later executions while the foundation-model parameters remain fixed.** — HOLDS — A saved but behaviorally inert artifact would defeat this premise, but the note describes committed interface, memory, capability-map, and router state that later executions consume.
6. **Those retained harness components are behavior-shaping enough that changing them counts as changing deployed-system behavior rather than merely updating bookkeeping.** — HOLDS — Logs or annotations would be counterexamples, but task interface, memory, capability availability, and routing all sit directly on the behavior path described in the note.
7. **A zero historical-loss budget over sampled anchors warrants only sampled-anchor protection, not a general no-regression conclusion.** — HOLDS — The strongest counterexample would be complete coverage of all materially relevant prior behavior, but the note explicitly limits the count to sampled anchors and cites held-out forgetting even under strict sampled-anchor protection.
8. **HCL's four-part partition and update-permission ablations do not by themselves establish those parts as the correct causal units for predicting local impact or bounding spillover.** — HOLDS — A defeater would be experiments that isolate one part and repeatedly show bounded downstream effects across tasks, but the note reports only permission bundles inside a fixed engineering partition.

## For the human
Look first at premise 1: if architecture alone does not earn the deployment-time label outside actual deployment, the note's headline classification needs rescoping before its selective-evaluation caution matters.
