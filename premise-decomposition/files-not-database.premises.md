# Premise decomposition: Incrementally constrained files defer centralized schema commitment until write invariants stabilize

**Note:** kb/notes/files-not-database.md
**Register:** claim
**Central commitment (one sentence):** When shared file and Git tooling makes authored documents cheap to inspect and revise, canonical writes tolerate weak enforcement, and added read capabilities remain rebuildable, files should retain authority while constraints stabilize, whereas database authority is warranted when correctness requires stable write-time invariants or mutable state that no document can safely own.

## Premises and counterexamples
1. **A file-backed canonical store can postpone centralized enforcement while retaining schema as revisable filenames, directories, frontmatter, link labels, and validators.** — HOLDS — The counterexample hunt considered repositories whose canonical branch rejects every write against a strict schema and repositories with many consumers coupled to path and frontmatter conventions; these cases make file constraints binding, but only after the operator has chosen centralized validation or consumers have entrenched the conventions, so they do not show that a file-backed store cannot defer that enforcement while requirements remain unsettled.
2. **When agents already share file and Git tools, canonical files provide an immediately usable authoring and inspection surface without requiring a storage-specific API or purpose-built viewer.** — HOLDS — A managed platform with excellent database tools was the strongest candidate counterexample, but it reverses the premise's tooling condition and is expressly routed by the note to the case where database infrastructure is the cheaper shared substrate; under the stated condition, ordinary editors, repository browsers, and agent file operations remain usable.
3. **The information needed by later enforcement can be recognized and retained while enforcement itself is postponed.** — DOUBTFUL — An exploratory provenance KB may initially preserve source text and Git authorship but not the capture-time signer identity and original retrieval timestamp that a later chain-of-custody invariant requires; once several sources have been copied by the same automation account, those facts cannot be reconstructed from the documents or repository history. The instruction to capture stable identity and provenance from the first record is correct only when the future-required facts are already recognizable, a condition the note does not state. — LOCAL — instance
4. **A read-side structure reconstructed entirely from canonical documents and declared derivation inputs can remain non-authoritative if stale copies are checked against their source or omitted.** — HOLDS — The counterexample hunt considered corrupted indexes, embedding-model changes, long rebuild times, and temporary unavailability; corruption and model changes are handled by retaining derivation inputs and rebuilding, while rebuild latency affects availability but does not make the view an independent source of retained information.
5. **The need for a stable invariant at canonical write time is by itself sufficient to prefer database authority over canonical files.** — DEFEATED — A low-throughput documentation repository can require globally unique stable IDs and atomic multi-file link updates while a serialized Git merge queue runs a whole-repository validator before advancing the protected canonical branch. Invalid candidate branches never become canonical, and each accepted Git commit publishes all affected files atomically, so the invariant holds at write time without database authority. This case contradicts the stated database boundary even though it uses the note's own file-and-validator progression. — GLOBAL — instance
6. **When mutable state cannot be assigned safely to one document, it requires an authoritative coordination substrate rather than a rebuildable read view, and a database can provide that substrate.** — HOLDS — First-class edge documents and append-only event files were candidate defeaters, but they work precisely by giving each relation or event safe canonical ownership; they do not defeat the narrower premise about state for which no such ownership assignment is safe.
7. **Whether a supporting store can be discarded and rebuilt from authored documents without information loss or correctness failure distinguishes a derived view from authoritative state.** — HOLDS — Expensive rebuilds, nondeterministic embeddings, and externally referenced generated identifiers were considered: cost alone does not create independent truth, while irreproducible embeddings or externally meaningful identifiers fail the stated rebuildability test and are therefore correctly routed out of the derived-view class.
8. **Because a flexible database can also postpone normalization, the case for canonical files depends on contingent authoring and inspection costs rather than on databases being inherently rigid.** — HOLDS — A JSON document table confirms rather than defeats this premise: it can defer field-level schema commitments, so the substrate decision must turn on the available toolchain and required correctness properties as the note states.

## For the human
Look first at premise 5: canonical Git publication can enforce some stable write-time invariants over files, so the boundary needs the narrower condition that the required invariant cannot be enforced safely and cheaply at the file store's canonical-write boundary.
