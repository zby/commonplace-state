# Premise decomposition: Traditional debugging intuitions break when tool loops can recover semantically

**Note:** kb/notes/traditional-debugging-intuitions-break-when-tool-loops-can-recover.md
**Register:** claim
**Central commitment (one sentence):** In framework-owned tool loops that permit semantic recovery, successful task completion is insufficient evidence that the intended mechanism is healthy, so programmers carrying over traditional debugging intuitions can overlook broken infrastructure and let it persist.

## Premises and counterexamples
1. **Programmers trained on ordinary application software often infer from successful output and no visible failure that the intended machinery basically worked.** — DOUBTFUL — The note gives no prevalence basis for “often,” and observability-first practice may be ordinary among the operators most likely to maintain tool-loop infrastructure: they may routinely inspect traces, component metrics, or degraded-mode signals despite a successful result. — GLOBAL — prevalence
2. **Most recovery in traditional software is engineered in advance rather than synthesized semantically at runtime.** — HOLDS — Conventional planners, policy engines, and learned components can choose unenumerated-looking routes at runtime, but the note restricts the comparison to ordinary application software, and those cases do not establish that dynamically synthesized recovery is the prevalent form there.
3. **In ordinary application software, task success is usually a usable proxy for the intended machinery having mostly worked because an absent recovery path usually produces a visible failure and an implemented fallback is inspectable.** — DOUBTFUL — In distributed and layered applications, retries, caches, circuit breakers, exception containment, and partial-result behavior may routinely mask a component failure from the programmer observing only the end result; if that is ordinary rather than exceptional, the proxy is already weak in the comparison class. — GLOBAL — prevalence
4. **When a framework-owned loop exposes a tool failure to an LLM and leaves alternative actions available, the LLM can infer the task intent and construct a viable path that was not selected from a pre-specified fallback menu.** — HOLDS — A terminating tool protocol, a hidden error, missing permissions, or lack of an alternative would prevent recovery, but each removes a stated condition; none defeats the conditional capability.
5. **Semantic recovery is qualitatively different from exception handling because only the former can construct a runtime path instead of selecting a fixed fallback.** — DEFEATED — A conventional exception handler can invoke a planner or constraint solver that searches available actions after observing runtime state, producing a path that was not enumerated as a fixed fallback; the relevant distinction must therefore be narrower than path construction versus fixed selection. — LOCAL — instance
6. **Semantic recovery can yield a successful final artifact even though the intended helper or script failed.** — HOLDS — A loop that receives a helper failure and then uses another available tool to obtain the same needed information is a coherent witness; cases where no substitute exists do not refute this existential capability.
7. **When both the intended path and a recovery path can produce the same successful outcome, the outcome alone cannot identify whether the intended mechanism was healthy.** — HOLDS — An artifact might accidentally contain path-specific clues, but then the observer is using more than success alone; without path evidence, the two executions remain observationally compatible with the same outcome.
8. **Programmers often stop investigating after a good artifact, rather than inspect the execution path for recovered failures.** — DOUBTFUL — The claimed tendency is unsupported in the note, and teams operating agent infrastructure may commonly review tool traces, alerts, or failed-call telemetry even when the artifact is good; establishing that such practice is not prevalent requires comparative evidence about actual maintenance behavior. — GLOBAL — prevalence
9. **When semantic recovery hides a helper failure from both the final result and any independent health signal, the missing repair trigger can allow that helper to remain broken and infrastructure drift to accumulate.** — HOLDS — Scheduled tests or path-level monitoring would surface the failure, but those mechanisms violate the premise’s absence-of-independent-signal condition; no counterexample was found within the stated condition.

## For the human
Look first at premise 3: the note’s contrast depends on task success being a meaningfully stronger health proxy in its traditional-software comparison class, and that prevalence claim needs support or a narrower scope.
