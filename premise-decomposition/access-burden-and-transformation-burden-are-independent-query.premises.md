# Premise decomposition: Access burden and transformation burden are distinct query dimensions

**Note:** kb/notes/access-burden-and-transformation-burden-are-independent-query.md
**Register:** claim
**Central commitment (one sentence):** Question answering is usefully decomposed into access burden and transformation burden as distinct dimensions that can vary separately while interacting in an iterative execution loop, after which fully specified work should be routed to trustworthy symbolic execution and unresolved judgment to bounded semantic calls.

## Premises and counterexamples

1. **At any point in answering a query, locating the inputs currently needed and deriving a requested result from available inputs remain distinguishable roles, even if one operation contributes to both.** — HOLDS — The strongest challenge is an adaptive investigation in which reasoning determines what evidence to seek and each retrieval changes the reasoning problem. That interleaving makes the boundary state-dependent, but it does not make the roles identical: proposing a hypothesis transforms available evidence, while obtaining the record that tests it supplies an input.
2. **There can be queries with high access burden and low transformation burden, and other queries with low access burden and high transformation burden.** — HOLDS — A buried literal answer requires difficult search followed by identity-like extraction, while records in a known table can be immediately accessible yet require nontrivial selection and aggregation. Because this is a possibility claim, a case in which both burdens rise together would not defeat it.
3. **Retrieval or reasoning can change the other burden without preventing access burden and transformation burden from remaining distinct diagnostic dimensions.** — HOLDS — A cached result can reduce the remaining transformation to extraction, and causal analysis can reveal a missing record that creates a new access step. Both cases alter the amount of remaining work but still permit the system to say whether its next obstacle is obtaining evidence or operating on evidence already present.
4. **Treating query difficulty as one score always obscures where work remains and which mechanism could reduce it.** — DEFEATED — For a direct lookup whose key and value are already present and whose requested output is the value verbatim, a scalar assessment of negligible difficulty leaves no material residual work or mechanism choice to obscure. The decomposition remains available and useful for nontrivial cases, but the unqualified consequence does not hold for every query. — LOCAL — instance
5. **A next transformation can be separated into components whose procedures and acceptance conditions are fixed and components that still require interpretation, relevance judgment, synthesis, explanation, or conjecture.** — HOLDS — Ambiguous text-to-SQL initially appears to challenge the split because schema access can change which operation is intended, but the ambiguity is itself unresolved specification work; once resolved, the query construction and execution can be split again. Mixed and iteratively reclassified work are expressly allowed rather than counterexamples.
6. **Once an executable procedure and its acceptance conditions are explicit, a symbolic substrate can perform that procedure without supplying semantic judgment during execution.** — HOLDS — Sampling and other multi-output procedures do not defeat this premise because the distribution and acceptance conditions, rather than one literal result, can be specified. Representation errors, implementation defects, and wrong specifications can still yield wrong answers, but the note explicitly excludes those from the execution guarantee rather than assuming symbolic execution prevents them.
7. **Whenever a trustworthy symbolic implementation exists, it should perform the whole fully specified operation rather than let an LLM participate in its execution.** — DOUBTFUL — In a finite-domain operation such as normalizing one of four enum values, deterministic model decoding can be exhaustively checked over every allowed input; if the model is already running and a separate tool invocation has meaningful latency or failure cost, model execution can satisfy the exact acceptance conditions without the reliability or cost disadvantage used to support the universal routing preference. This is a deliberately fenced case, but the premise does not state a condition that excludes it or allow a generate-and-symbolically-verify route. — LOCAL — priced-exception
8. **Transformation can expose missing evidence, retrieval can change the transformation that remains, and validation can change either, so routing may need to repeat rather than end after one access stage and one transformation stage.** — HOLDS — A causal expense analysis can reveal that contract dates are missing, and validating a computed total against the user's request can reveal that refunds were wrongly included. These concrete cases support the note's possibility claim; a query that completes in one pass would not defeat it.

## For the human

Look first at premise 7: the routing preference needs to say whether a fully specified operation may use an exhaustively verified model path or model-generated candidates with symbolic validation when that path preserves exact acceptance while improving end-to-end cost.
